# Version-bound ingress update transport

`scripts/docker_context_api.py` supplies one bounded Engine service-update request through the existing protected Visitaki Docker SSH context. Importing it performs no I/O. The caller supplies the original service ID, original positive version, and complete intended spec; the request uses that exact version rather than re-inspecting a newer version inside Docker CLI.

The context must be named `visitaki-ingress-<run>-<attempt>` and resolve to `ssh://makepad@135.181.141.31`. Each metadata read and the single update request has a 30-second subprocess timeout. Each CLI starts in its own session; a timeout kills only that owned process group, then allows five seconds to drain/reap and one final second to reap after closing pipes. An unverified cleanup is an error, never acknowledgement. The JSON request is limited to 1 MiB and accepted response output to 72 KiB, with a 64 KiB decoded body limit. Docker output is not included in errors. Only a complete HTTP 200 JSON-object response acknowledges the update. Failure or an ambiguous response is never retried and does not authorize rollback.

The transport uses Docker CLI's internal `docker system dial-stdio` command with the explicit selected context, retaining the workflow's isolated SSH configuration. The command is hidden and is not a stable public interface; an incompatible CLI or response refuses without a fallback transport. Its supported implementation is documented in [Docker CLI source](https://github.com/docker/cli/blob/master/cli/command/system/dial_stdio.go). Version-based service updates are documented in the [Engine API](https://docs.docker.com/reference/api/engine/version/v1.51/).

Callers remain responsible for exact-spec convergence checks, endpoint verification and ownership-bound recovery. This module does not itself deploy, poll, or roll back. Normal policy CI and Visitaki pre-deployment validation run `python3 -m unittest ./tests/test_docker_context_api.py`; transport responses are mocked, while the timeout regression starts only a disposable Python parent and descendant and proves both stop within the bound.

Normal CI also runs `scripts/test-docker-context-api.py` against `docker:29.10.1-dind@sha256:fbbc96e0af32cdc190aff92ba97a1281a115351a723afe21af78879cc55126b0`. That fixture starts one owned privileged daemon container with no network or published ports, mounts only a new private socket directory, and uses a private Docker client configuration. It initializes Swarm only inside that disposable daemon, creates a zero-replica service, then verifies an actual Engine HTTP 200, exact candidate readback and rejection of a stale original version. It removes only its own daemon container and anonymous volume and verifies the shared daemon's Swarm state is unchanged. The operation budget is 240 seconds plus bounded cleanup; image download is within that budget. No host Docker socket, credentials, service or daemon-data directory is mounted into the fixture.

The fixture exercises the actual Engine and CLI over the isolated Unix socket. It does not exercise SSH end to end or establish production rollout acceptance. Production's exact SSH allowlist has no fixture/environment override. If the CI host cannot provide the pinned isolated daemon, the fixture fails rather than testing against the shared daemon.
